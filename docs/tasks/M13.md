# Task M13: how often does the guest main loop get a zero or odd time step? (probe only, env PS2X_SYNCV_LOG=1)
Budget: "[call N/12]", stop at 12. Edit ONLY PS2Recomp/ps2xRuntime/src/lib/Kernel/Stubs/GS.cpp (sceGsSyncV at L1392, which calls ps2_syscalls::WaitVSyncTick) and, if needed, the .cpp that implements WaitVSyncTick (Kernel/Syscalls/*) and EeScheduler.cpp. No headers. DO NOT BUILD/RUN/COMMIT. Mark `// PROBE-M13`. Static bool read once; unset = one bool test.
Why: particle effects (and other EE physics) in the port occasionally contain +-FLT_MAX positions (spike polygons) and the game also triggers a slow-motion/blur effect in places where PCSX2 does not. Both could come from a per-tick time step that is 0 or odd in our emulation (division by zero => +-FLT_MAX on PS2). The main loop (guest 0x51DF88) paces itself with sceGsSyncV(0) (guest 0x404198, called from 0x51E3C8 / 0x51E47C). On real hardware each call returns exactly once per vsync. Also other time sources the game may use: COP0 Count (mfc0 $9), EE timers T0-T3 COUNT registers (0x10000000, 0x10000800, 0x10001000, 0x10001800), the vblank counter updated by the GS vsync interrupt handler.
Do (only when PS2X_SYNCV_LOG=1):
1. In sceGsSyncV: record for each call the guest vblank counter value on entry and on return (use whatever counter the scheduler exposes: VBlankStart count) and the host time. Keep a histogram per second of (a) delta vblanks between consecutive RETURNS: 0, 1, 2, 3, 4+ ; (b) how many calls returned without waiting at all (entry==exit); (c) min/max/avg host ms between consecutive returns; (d) which thread id called (must be tid 1, print if not). Print `[syncv] n=%u d0=%u d1=%u d2=%u d3=%u d4p=%u nowait=%u hostMs(min/avg/max)=%.1f/%.1f/%.1f ifreq=%d` once per second (ifreq = g_gparam.interlace value used in the call).
2. Also once per second print the raw values the guest could read as time: the current value of COP0 Count as our runtime reports it, EE timer T0 COUNT / T1 COUNT (as returned by the runtime's IO register read, address 0x10000000 / 0x10000800), and the delta since the previous second, as `[time] count=%u dCount=%u t0=%u dT0=%u t1=%u dT1=%u hostMs=%.1f` so we can see whether our emulated clocks advance at the real rate (real: Count advances 294912000 per second; T0/T1 depend on their mode, report as is).
3. No change to behaviour.
